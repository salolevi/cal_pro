Phase 0 · Screen Structure

CalorAR Wireframes

Five core screens, drawn as structure rather than surface. Every decision here is cheap to change now and expensive to change once SwiftUI assumes it.

These are wireframes, not mockups. No color, no typography, no icons — dashed boxes mean "something goes here." If you catch yourself reacting to how they look rather than what's on them, they're failing at their job.

1.5 Meta
Sign in with Apple sits above emailApple requires offering it once any other third-party login exists. Putting it first also removes the highest-friction step from the highest-abandonment screen.
The calculated target is a default, not a cageStep 1.5 shows the computed number and an explicit "Ajustar manualmente" beside it. The plan called for this; the wireframe is where it becomes visible rather than aspirational.
Sex is asked with a stated reasonIt's an input to Mifflin–St Jeor, not a profile decoration. The one-line explanation costs nothing and prevents the field reading as gratuitous.
One question per stepA single form with nine fields reads as work. Four short steps with a progress indicator read as progress — and let you drop someone back in mid-flow.
Implications for what's already built
  • Steps 1.2–1.4 map exactly onto profiles: sex, birth_date, height_cm, activity_level, goal.
  • Step 1.5 writes calorie_target and the three macro target columns — all four already nullable and overridable.
  • Current weight is a weight_logs row, not a profile column. Onboarding therefore writes to two tables, and the first weigh-in seeds the trend chart on screen 5.
  • The activity_level enum values (sedentario … muy_activo) are the five options verbatim — no mapping layer needed.
  • The ritmo slider writes weekly_rate_kg, added in migration 20260816000000. Combined with goal it produces the daily delta applied on top of TDEE.

Resolved: ritmo now has a home — weekly_rate_kg numeric(3,2) on profiles, capped at 2 kg/week. The slider stays rather than being replaced by fixed per-goal deltas, which keeps the pace of loss an explicit user choice instead of a hidden constant.

2.1 Con resultados
kcal per serving, not per 100 gThe database stores per 100 g because that's the sane canonical form. Nobody thinks in 100 g. The row shows "1 vaso · 122 kcal" and does the conversion for you — this is the single highest-value translation in the app.
Brand on the second line, product firstPeople search "leche" far more than "serenísima". The weighted tsvector already ranks name above brand; the layout should agree with the ranking.
Verified badge on every rowBulk-imported Open Food Facts rows sit next to hand-curated ones. Showing which is which is both the trust signal and the liability mitigation the plan called for — and it tells you where curation effort is still needed.
The empty state is the real screenMost logging is repetition. Before a query is typed, this screen should show recientes and favoritos — not a blank page with a cursor. That state gets used more than the results state.
"¿No lo encontrás?" is visible but quietIt captures the gap when the catalog misses. Wired up in the crowdsourcing phase; until then it's the clearest signal of what's missing.
Implications for what's already built
  • Rows come straight from search_products(q) — it already returns name, brand, kcal, serving size and label in one call.
  • is_verified drives the badge, and is already a tiebreaker in the function's ORDER BY.
  • Per-serving kcal is calories_kcal × serving_size / 100. Products with a null serving_size have no serving row to show — the layout needs a per-100 g fallback.
  • The empty state needs a query the schema does not yet serve: recent and favourite products. Recents are derivable from diary_entries; favourites are not modelled at all.

Gap found by drawing this: "Favoritos" is in the MVP scope table but has no table. It needs either a favourites join table or a boolean derived from logging frequency. Worth deciding before Phase 2 rather than bolting on later.

3.1 Detalle
Two ways in, one of them defaultThe serving row is prefilled from the product, so the common case is "1 × 1 vaso" and a single tap. The exact-amount row underneath handles everything else without making the common case pay for it.
Unit selector, not a fixed unitg, mg, ml, l. Anything the label uses. Conversion to the product's basis_unit happens before the write, so the stored value stays canonical.
"Añadir ahora" is the primary actionMost logging happens while eating. One tap stamps the current instant — no picker, no meal taxonomy, no decision.
"Agregar…" covers the restOpens a date and time picker for anything logged late or backfilled. Secondary weight, because it's the less common path — but it must allow past times, which is the whole reason it exists.
Macros recalculate liveDerived, never stored. Two glasses shows 244 kcal without a round trip — the arithmetic runs client-side off the per-100 values.
Provenance in the footer, quietlySource and verification date, small and at the bottom. Present for trust when someone looks; never competing with the numbers.
Implications for what's already built
  • Both buttons write one diary_entries row: product_id, quantity in basis_unit, and logged_at. "Añadir ahora" passes now(); "Agregar…" passes the chosen instant.
  • The serving row comes from serving_size + serving_label. Products with a null serving_size show only the exact-amount row.
  • Unit conversion is client-side: mg→g, l→ml. quantity is always stored in the product's basis_unit, so no unit column is needed on the row.
  • Displayed macros come from nutrition_facts per-100 values × quantity ÷ 100. Nothing derived is persisted, so a corrected nutrition panel retroactively fixes every past entry.
  • The footer reads source and verified_at, both already on products.

Consequence worth knowing: storing only quantity in basis_unit means the diary shows "200 ml", not "1 vaso". Rendering "1 vaso" requires dividing by the product's current serving_size — so if that value is later corrected, historical entries redisplay differently even though the amount eaten never changed. Storing what the user actually typed would avoid it, at the cost of two more columns.

4.1 Diario
Remaining, not consumed"Te quedan 860" is the actionable framing. "Llevás 1.240" is trivia. Same data, different question answered.
Grouped by hour, not by meal nameOnly hours with entries appear, so the day builds itself as you log. No taxonomy to agree with before recording a snack, and it fits Argentine hours — an 18:00 merienda and a 22:00 dinner need no special case.
Macros on every row, in small typeP · C · G per product, subordinate to the kcal figure. Someone tracking protein can scan the column without opening anything; everyone else reads past it.
Each entry keeps its exact timestampThe hour is the grouping; 08:12 is the record. Preserving it makes editing unambiguous and leaves the door open to timing analysis later.
Weight sits above the food logWeigh-ins happen in the morning, in the same session as breakfast. It's one compact row that disappears once logged, not a permanent fixture.
Date stepper rather than a calendarYesterday is one tap. Full calendar navigation is a rarely-needed screen that shouldn't tax the common case.
Implications for what's already built
  • One query per day against diary_entries_user_time_idx, now ordered (user_id, logged_at desc) after migration 20260816000000.
  • Hour buckets are date_trunc('hour', logged_at) — verified working against the new column.
  • Totals are a sum over joined nutrition_facts, scaled by each entry's quantity — computed, never stored, so no drift.
  • Targets come from profiles; the ring is consumed ÷ calorie_target.
  • "Registrar peso" upserts weight_logs, the same write as the profile screen. Two entry points, one row per day enforced by the unique constraint.

Consequence of hour buckets: eating at 12:58 and 13:05 produces two groups seven minutes apart. Fixed meal slots never had that problem. If it grates in practice, the fix is grouping by gap — start a new block after 90 minutes of no logging — rather than returning to named meals. Worth watching in the beta rather than pre-solving.

Still not drawn: editing and deleting an entry. Tap a row to adjust quantity or time, swipe to delete. Mundane, but real Phase 2 work that belongs in the estimate.

5.1 Perfil
Target is directly editable, with recalculation as an escape hatchSomeone who has been given a number by a nutritionist should be able to type it in. "Recalcular desde mis datos" restores the computed value for everyone else.
Macros shown as grams and percentPercent is how splits are discussed; grams are what you log against. Showing one without the other forces mental arithmetic.
Weight logging lives here, not in the diaryFood is logged several times a day; weight weekly at most. Different rhythms, different screens.
Trend chart, not a table of weigh-insDaily weight is noisy. The direction over 90 days is the only useful reading.
Implications for what's already built
  • Everything in "Mis datos" and "Meta diaria" is a profiles update.
  • "Registrar peso" upserts weight_logs — unique (user_id, logged_on) already makes same-day corrections an upsert rather than a duplicate.
  • The chart reads weight_logs ordered by date; weight_logs_user_date_idx covers it.
  • "Comidas guardadas" navigates to saved_meals — modelled, and with no screen drawn yet.

Fourth tab is undecided. "Progreso" appears in the tab bar but has no wireframe. It could hold the weight chart and weekly averages — which would then make this screen purely settings. Worth resolving before Phase 2 starts.

Parked idea · not MVP
  • A character that reflects logging consistency. Shown "locked in" when the streak holds, "lost" when logging lapses — a state readable at a glance, without a number or a guilt-trip.
  • Consistency is already derivable: distinct days with entries in diary_entries over a trailing window. No new data needed, only a rule for the thresholds.
  • Deliberately out of MVP. It needs illustration work and a tone decision — a character that reads as disappointed is a fast way to make a calorie app feel punishing, which is the failure mode worth avoiding in this category specifically.
  • Best revisited after the beta, when there is real retention data showing whether people lapse at all and when.
Output

What drawing these surfaced

The point of wireframing was never the pictures. It was these five items, each of which is cheap to settle now.

✓ Resolved · Meal slots replaced by clock timeFixed Desayuno/Almuerzo/Merienda/Cena removed entirely. diary_entries.logged_at is a timestamptz, the meal_slot enum is dropped, and the diary groups by hour. Applied in migration 20260816000000.
✓ Resolved · Ritmo has a columnweekly_rate_kg numeric(3,2) on profiles, capped at 2 kg/week. Same migration.
✓ Resolved · Weight logging reachable from the diaryA compact row above the food log, upserting the same weight_logs table as the profile screen.
1 · Favoritos still has no tableIn MVP scope, and what the search empty state is built around, but nothing models it. Needs a favourites join table, or derive it from logging frequency and drop the star.
2 · The "Progreso" tab is undefinedIt exists in every tab bar drawn here and has no content. Either give it the weight chart and weekly averages, or cut to three tabs.
3 · Saved meals have no screenModelled in the schema, listed in MVP scope, absent from these five. Needs a list plus a "guardar esta comida" affordance in the diary.
4 · Products with no serving size need a fallbackserving_size is nullable and bulk-imported rows often lack one. With the new portion control, those products show only the exact-amount row — which is a reasonable answer, but it should be a decision rather than an accident.
5 · Displayed amounts lose the unit the user typedLogging "1 vaso" stores 200 ml, so the diary renders "200 ml". Recovering "1 vaso" means dividing by the product's current serving_size, which shifts historical display if that value is ever corrected. Two extra columns would fix it.
Suggested next step
  • Items 1 and 5 are schema changes and belong together in one migration before Phase 2 starts.
  • Items 2, 3 and 4 are scope and design decisions, legitimately deferrable to the start of Phase 2.

Wireframes are structure, not design. Colour, type, spacing and the app icon are Phase 3 work — deliberately absent here.
